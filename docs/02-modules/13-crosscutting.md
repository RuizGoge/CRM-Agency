## Silo enforcement as a data-layer capability (row-level scoping + the leaderboard exception)
**Verdict:** ADOPT - non-negotiable, ships in v1. This is the product's architecture, not a feature. Building it later means rewriting every query.  ·  **Complexity:** medium

**Why it matters here:** The defining architectural fact of this product is that each of the ~50 sellers sees ONLY their own book of business, with two deliberate holes: supervisor/admin global visibility, and a leaderboard that is PUBLIC to everyone. If isolation is enforced in React components instead of at the data layer, the first API endpoint someone adds leaks another seller's Final Expense leads — and in an insurance context that is a PII incident, not a bug.

**Behavior spec:** Every table carries tenant_id + owner_user_id. All reads go through a single scoping primitive resolving (actor_role, actor_id) -> predicate: seller = owner_user_id = me; supervisor/admin = tenant_id = mine. No query bypasses it; the default is deny. Exactly ONE explicitly whitelisted read path is public-within-tenant: the leaderboard projection, which exposes only {user_id, display_name, avatar, earnings_total, closed_won_count, rank, badge} and NEVER lead/contact/opportunity rows. Cross-seller URL probing (/opportunities/{id} for someone else's deal) returns 404, not 403, so seller A cannot even enumerate that seller B has a deal. Supervisor views are read-mostly and are visually marked (persistent 'Viewing as supervisor - Maria Delgado's book' bar) so oversight never gets mistaken for ownership. Aloware webhooks resolve ownership by matching the Aloware agent/user id -> our user, and any unresolvable event lands in an admin-only quarantine queue rather than being attached to a random seller.

## Event backbone: one append-only event log feeding timeline, automation, Earnings and leaderboard
**Verdict:** ADOPT - v1 backbone. Everything else in this list is cheaper because this exists; skipping it makes the leaderboard, timeline and automations three divergent sources of truth.  ·  **Complexity:** high

**Why it matters here:** House rule: this system is an ORGANISM, not a set of screens. The single most valuable behavior we build (auto-logging Aloware calls, disposition, recording, transcript, AloAi summary into the lead timeline) and the single most motivational one (Closed-Won -> Earnings -> re-rank -> celebration) are the SAME mechanism seen twice. If they are two separate code paths, the leaderboard and the timeline drift apart and the demo dies mid-pitch.

**Behavior spec:** One events table (tenant_id, actor, subject_type, subject_id, event_type, payload jsonb, occurred_at, recorded_at, source, idempotency_key). Plain-English event vocabulary only - lead.created, lead.went_cold, call.completed, sms.received, appointment.no_showed, opportunity.stage_changed, opportunity.closed_won - never a generic condition builder. Three consumers subscribe to the same stream: (1) the unified per-lead timeline with type filters (calls / SMS / email / notes / stage changes), (2) the automation engine whose triggers are bound directly to stages and to these event names, (3) projections - my_day activity list, funnel counters, and the leaderboard earnings rollup. occurred_at vs recorded_at is separate so a call webhook arriving 40s late still threads into the timeline at the right moment. Every event is replayable: rebuilding the leaderboard from scratch must be a single job, which is also how we later add a monthly period reset (filter the same stream by occurred_at) with zero redesign.

## Real-time updates between users (live leaderboard, live board, live timeline)
**Verdict:** ADOPT - v1. Directly mandated by the client's real-time leaderboard decision and by speed-to-lead. Use a managed realtime layer (Postgres LISTEN/NOTIFY or an equivalent hosted pub/sub) to stay inside the <$100/mo infra target for 50 concurrent users.  ·  **Complexity:** medium

**Why it matters here:** The client explicitly chose all-time AND real-time for the leaderboard, and it is the public motivational module. A leaderboard that needs F5 is not motivational, it is a report. It is also the demo money-shot: drag a card into Closed Won on the laptop and the TV kiosk re-ranks and celebrates within seconds, in front of the buyer.

**Behavior spec:** Server-push (WebSocket/SSE) with three channel classes matching the silo rules: tenant:{id}:leaderboard - public to every authenticated user in the tenant; user:{id}:stream - private, carries board moves, new inbound lead, call completed, SMS received, appointment changes; tenant:{id}:ops - supervisor/admin only. Payloads are event envelopes + the changed projection row, never full lead records, so the public channel physically cannot leak PII. Closed-Won propagation p95 < 2s from drop to every connected client including the kiosk. Reconnect does a since=<last_event_id> catch-up rather than a full refetch. Degraded fallback: if the socket is down, the leaderboard and board poll at 20s and show a subtle 'Live' / 'Reconnecting' pill - never a blocking error. Inbound-lead push is the same channel: a purchased FE lead lands and the seller's board shows it plus an audible/visual New lead - Call now toast without any refresh, because these leads decay in minutes.

## Cmd+K command palette that SEARCHES and EXECUTES
**Verdict:** ADOPT - v1, but scoped: ship FIND plus roughly 10 hard-coded DO commands. Reject any generic user-defined command registry as blank-canvas bloat.  ·  **Complexity:** medium

**Why it matters here:** Pattern 7 (Attio/Close) and the #1 conversion lever collide here: a purchased Final Expense lead is worth the most in its first 60 seconds. A palette where a seller types a phone number and hits Enter to place the call is a shorter path than any navigation. It is also the single cheapest 'this feels like a 2026 product, not GoHighLevel' signal in a 10-minute demo.

**Behavior spec:** Cmd/Ctrl+K anywhere, including inside the kanban and on mobile (a persistent search affordance in the bottom bar). Two result groups always visible: FIND and DO. FIND searches leads, opportunities, and activities scoped by the silo rules (a seller literally cannot surface another seller's lead), matches on name, email, normalized E.164 phone with partial matching so typing 5127 finds (512) 7xx-xxxx, policy/opportunity id, and carrier. DO executes verb-first commands with the current context pre-bound: 'Call now', 'Log call', 'Send SMS' (blocked with an inline reason if the TCPA consent flag is false or the number is DNC-suppressed), 'New lead', 'Move to Quoted', 'Schedule appointment', 'Mark Closed Won' (which opens the required annual-premium field inline rather than failing), 'Add note', 'Open leaderboard', 'Open kiosk view'. First keystroke to first result p95 < 150ms via a local index of the seller's own book (a seller owns hundreds, not millions, of records - this is tractable). Recent objects show before typing. Every command is also reachable by mouse, so the palette is an accelerator, never the only path.

## Keyboard shortcuts for the daily grind (dial, dispose, advance, next)
**Verdict:** ADOPT - v1. Cheap, high perceived quality, and directly serves the dial-dispose-next loop that FE telesales runs on.  ·  **Complexity:** simple

**Why it matters here:** A Final Expense seller working an agent-paced Power Dialer queue repeats the same four actions a hundred times a day: dial, dispose, note, next. Every mouse trip is friction multiplied by 100. This is also what separates us from the 'simple to use, brutal to administer' tools we listed as an anti-pattern - speed for the person actually on the phone.

**Behavior spec:** Single-key shortcuts active when no input is focused: c = Call now on the focused lead, s = Send SMS, n = Add note, e = Log email, a = Schedule appointment, j/k or arrows = move focus between kanban cards, 1-9 = move focused card to stage N (stage-gating still applies), / = focus search, ? = shortcut cheat-sheet overlay, Esc = close/cancel (and cancels a pending optimistic action). In the Power Dialer / My Day working view, Space = next lead after a disposition is set. Shortcuts are discoverable: every menu item and button renders its key hint, and the ? overlay is one screen grouped by context. No user remapping in v1. On mobile these degrade to thumb-reachable primary actions rather than being emulated.

## Performance budgets treated as a product feature with visible SLOs
**Verdict:** ADOPT - v1. Without numeric budgets the speed claim is marketing. Keep the budget list to these five; more becomes ceremony.  ·  **Complexity:** medium

**Why it matters here:** Speed-to-lead is stated as the #1 conversion lever: purchased FE leads arrive by ping-post and decay in MINUTES. 'Fast' as a vibe degrades silently across a vibecoded build; 'fast' as a numeric budget with a CI gate does not. This is also the honest differentiator we claimed in Phase 0 - simplicity + speed.

**Behavior spec:** Five budgets, each with a p95 target, measured in production and asserted in CI on a seeded 50-seller / 15k-lead dataset: (1) ping-post/webhook intake -> lead visible on the owner's board and pushed to their client < 3s; (2) 'Call now' tap -> Aloware Two-Legged Call API accepted and UI confirmed < 800ms; (3) kanban board first meaningful paint with 300 cards on simulated 4G < 1.5s; (4) Closed-Won drop -> leaderboard re-ranked on all clients < 2s; (5) Cmd+K first results < 150ms. Budgets are enforced structurally: board pagination/virtualization per stage column, leaderboard served from a precomputed projection (never a live SUM across opportunities at read time), timeline paginated by occurred_at. Violations surface in the admin health panel, not only in a dashboard nobody opens. Bundle budget for the mobile route set is capped and checked at build time.

## Responsive with an explicitly mobile-first contact surface (not a shrunken desktop)
**Verdict:** ADOPT - v1, with the omission list written into the spec. Declaring what mobile does NOT do is what prevents the afterthought failure mode.  ·  **Complexity:** medium

**Why it matters here:** Phase 0: desktop for management, mobile for quick contact - and 'mobile as an afterthought' is on our anti-pattern list. A seller driving between appointments needs to answer a callback, log what happened, and move the card. They do not need to configure a pipeline from a phone.

**Behavior spec:** Two deliberate experiences over one codebase. MOBILE ships full-fidelity: My Day activity list, lead detail with unified timeline, one-tap Call now / SMS / note, disposition capture, stage change via a stage picker (not drag), appointment scheduling, and the leaderboard (which people check on their phone precisely because it is social). Primary actions live in a thumb-reachable bottom bar; tap targets >= 44px; phone numbers are tel:-linked and extension-friendly. MOBILE deliberately omits: pipeline/stage configuration, automation template editing, CSV import, user management, kiosk mode - these render a 'Open on desktop' card instead of a broken mini-form. DESKTOP owns kanban drag-and-drop, bulk work, configuration, supervisor rollups. Breakpoints are content-driven; the kanban becomes a single-column stage list under 900px rather than a horizontally scrolling toy.

## First-run onboarding with realistic US life-insurance demo data (the demo-sellability engine)
**Verdict:** ADOPT - v1, and treat it as a first-class deliverable rather than test fixtures. This is the single highest ROI item in this list for sellability.  ·  **Complexity:** medium

**Why it matters here:** A CRM demoed on empty screens sells nothing, and lorem-ipsum data ('Test Lead 1', $1,000 deals) actively signals a toy to an insurance agency owner who knows what an FE lead card looks like. Realistic seeded data is what makes the 10-minute demo land: a populated board, a plausible leaderboard with 8 named sellers, and a Closed-Won drag that moves real-looking money.

**Behavior spec:** One idempotent seed command generates a believable tenant: 8 sellers with US names (Marcus Whitfield, Danielle Ortiz, Ray Kowalczyk, Tanya Brooks...), ~180 leads across the FE and IUL pipelines. Demographics match the vertical: FE prospects aged 58-80 in TX/FL/GA/OH/NC with annual premiums $540-$1,450 (i.e. $45-$120/mo, the real FE band) and carriers like Mutual of Omaha, Americo, Foresters, GTL; IUL prospects aged 32-52 in higher-income metros with annual premiums $2,400-$12,000 and carriers like Pacific Life, National Life Group, Allianz. Lead sources reflect reality: Purchased FE lead (ping-post vendor), Direct mail FE card, Facebook lead form, Aged FE list, Referral, Inbound call - each purchased lead carrying a consent-certificate stub and a TCPA consent flag so the compliance rails are visible in the demo. Timeline history is pre-threaded: call attempts with dispositions (no answer, voicemail, contacted), an AloAi-style call summary, SMS exchanges, and stage changes with realistic dwell times so 'days since last touch' and the cold-after-7-days badge are already firing on some cards. Loss reasons are distributed across the six typified reasons. The leaderboard therefore opens with a real podium and a real spread. Demo mode is a labeled, one-click resettable tenant, never mixed into a live tenant. For real first-run, a 4-step checklist replaces it: connect Aloware, confirm your pipeline template, import or add your first lead, connect Google Calendar.

## Compliance rails as a cross-cutting concern (TCPA consent flag, DNC, opt-out, calling hours, CCPA)
**Verdict:** ADOPT - v1. Aloware covers the carrier-side obligations; this covers ours. Cutting it converts a demo asset ('look, it won't let you dial that') into a legal liability.  ·  **Complexity:** medium

**Why it matters here:** TCPA and CCPA were named as design-time constraints, and the ping-post lead economy is exactly where TCPA litigation lives. Aloware natively handles STIR/SHAKEN, A2P 10DLC, DNC suppression, TCPA gating before SMS and STOP handling - but OUR app is where the consent certificate is stored and where a seller can accidentally try to dial a number they shouldn't. The rail must exist on our side of the line too.

**Behavior spec:** Every contact carries consent_status (express_written / express / none / revoked), consent_source, consent_captured_at, consent_certificate_url (the lead-vendor certificate stored at intake), dnc_flag and opt_out_at. A single guard function is called by every outbound path - Call now, Send SMS, sequence enrollment, Power Dialer list build, bulk action - and returns allow / block / warn with a human reason ('Contact replied STOP on Jul 12 - SMS blocked', 'Outside permitted calling hours in the contact's time zone (7:12 AM local)'). Blocked actions render disabled with the reason inline; they never fail silently and never throw a raw error. STOP/opt-out webhooks from Aloware flip the flag and write a timeline event within seconds. CCPA: a per-contact 'Export data' and 'Delete contact' admin action produces a machine-readable bundle and a tombstoned delete that preserves aggregate Earnings integrity (the closed opportunity's value survives; the PII does not). All consent state changes are events, so the audit trail is the same backbone as everything else.

## Time zone and calling-window correctness as a system primitive
**Verdict:** ADOPT - v1. Cheap if decided up front, brutal to retrofit, and it directly protects the TCPA rail and the appointment-reminder feature.  ·  **Complexity:** medium

**Why it matters here:** 50 sellers working US leads across four+ time zones is not an edge case, it is Tuesday. 'Days since last touch' driving the cold-at-7-days rule, appointment reminders, the My Day list, and the TCPA 8am-9pm calling window are all wrong unless timezone is modeled deliberately - and each wrong one is visible to the client (a no-show caused by a reminder sent at 4 AM is unforgivable).

**Behavior spec:** All timestamps stored UTC. Every contact stores a resolved timezone (derived from area code / ZIP at intake, editable); every user stores their own. Rendering rules are fixed per surface: lead detail and appointment times show BOTH the contact's local time and the seller's when they differ ('Thu 2:00 PM CDT - 12:00 PM your time'); the calling-hours guard evaluates against the CONTACT's local clock; appointment reminder scheduling uses the contact's local clock; My Day, the 7-day cold rule and the leaderboard day boundary use the SELLER's clock; supervisor rollups and the tenant leaderboard use one declared tenant timezone so 'today' means one thing in reporting. DST transitions handled by storing IANA zone ids, never fixed offsets.

## Idempotent, replayable ingestion for Aloware webhooks and ping-post lead intake
**Verdict:** ADOPT - v1. This is the reliability substrate under the auto-call-logging promise; without it that feature is a demo trick that rots in week two.  ·  **Complexity:** medium

**Why it matters here:** Auto-logging calls via webhooks is explicitly our highest-value integration behavior, and it is entirely at the mercy of at-least-once delivery, out-of-order arrival, and retries. Duplicate call events mean a polluted timeline; duplicate lead posts mean the seller calls the same person twice - which is both embarrassing and a TCPA aggravator. Duplicate closed-won events mean the leaderboard lies, which destroys the one module built on trust.

**Behavior spec:** Every inbound webhook and ping-post payload is written to a raw_inbound_events table first (signature-verified, full body, received_at) and processed asynchronously. A deterministic idempotency_key (provider + provider_event_id, or a hash for providers that don't supply one) enforces exactly-once effect via a unique constraint. Out-of-order handling: events are ordered by occurred_at when threading the timeline, and a late-arriving recording/transcript/AloAi-summary event PATCHES the existing call record instead of creating a second entry. Failed processing goes to a dead-letter queue with an admin retry button, never a silent drop. The raw log makes replay possible after a mapping bug - reprocess the last 24h instead of losing the day's calls. Ping-post intake additionally runs the dedupe check on normalized phone/email before creating a lead.

## Optimistic UI with undo instead of confirm dialogs
**Verdict:** ADOPT - v1, with the exception list written into the spec. The undo window on Closed-Won is the tricky part and must be designed alongside the leaderboard projection.  ·  **Complexity:** medium

**Why it matters here:** The core gesture of this product is ONE kanban drag that updates the record, fires automation, updates Earnings and re-ranks the leaderboard. A confirm dialog on that drag would kill the exact moment the whole demo is built around, and would tax the seller a hundred times a day. Undo is faster than confirm for reversible work.

**Behavior spec:** Reversible actions apply instantly in the UI and reconcile with the server behind a 5-second undo toast ('Moved Ellen Rhodes to Quoted - Undo'). Side effects that are themselves reversible (stage automations, Earnings recompute, leaderboard re-rank) are held for the undo window or compensated on undo, so an undone Closed-Won correctly un-ranks. On server rejection the card animates back to its origin with an inline reason, never a modal. THE EXCEPTIONS, spelled out because 'no confirm dialogs' as an absolute is wrong here: anything that leaves the building or cannot be recalled REQUIRES an explicit confirm - sending an SMS or email, placing a call, enrolling a lead in a sequence, bulk actions over ~10 records, CSV import commit, deleting a contact under CCPA, and changing pipeline configuration for the whole tenant. Closed-Won is not a confirm; it is a required-field gate (annual premium) plus a celebration plus undo.

## Skeletons over spinners, and a defined loading/empty/error state per surface
**Verdict:** ADOPT - v1. Low cost, high polish, and directly supports the perceived-performance claim.  ·  **Complexity:** simple

**Why it matters here:** Perceived speed is part of the speed claim. A skeleton board that already shows five stage columns reads as instant; a centered spinner reads as broken. In a live demo over hotel wifi this is the difference between 'snappy' and 'let it load'.

**Behavior spec:** Every data surface declares four states: skeleton, empty, error, loaded. Skeletons mirror the real layout - kanban shows stage columns with 3 ghost cards each, the leaderboard shows a ghost podium plus 7 ghost rows, the timeline shows ghost entries. Skeletons appear only after ~120ms so fast loads never flash. Realtime-driven regions never flip back to skeleton on reconnect; they keep last-known data plus a 'Reconnecting' pill. Spinners survive only inside buttons for a discrete in-flight action (Sending..., Placing call...). Error states are actionable and specific ('Couldn't reach Aloware - your note was saved, call logging will catch up. Retry'), never a raw stack or a generic toast.

## Import / export with dedupe at the point of entry and a merge review queue
**Verdict:** ADOPT - v1 for CSV import + dedupe + export; ADOPT LATER for the fancier fuzzy-match scoring. Ship the review queue in v1 even if the matching rules are simple - the queue is the pattern, the scoring can improve.  ·  **Complexity:** medium

**Why it matters here:** Sellers arrive with an existing book in a spreadsheet, and FE agents buy list drops constantly - so import IS onboarding for a 50-seller rollout. 'Dedupe as a manual chore' is on our anti-pattern list, and duplicates in this vertical are not cosmetic: two agents' worth of call attempts on one grandmother is a TCPA problem.

**Behavior spec:** CSV import with column mapping, a saved mapping per source, a mandatory preview showing row counts, and per-row validation errors before commit. Import is silo-respecting: a seller imports into their own book only; admins can import on behalf of a named seller. Dedupe runs at BOTH intake paths (ping-post/API and CSV) on normalized E.164 phone and lowercased email, plus a soft signal on name+ZIP. Exact matches are auto-linked to the existing contact and logged as a new touch; probable matches land in a MERGE REVIEW QUEUE with a side-by-side diff and a single merge action that preserves the union of timeline events. Import requires a consent/source column for purchased lists and refuses to mark a lead SMS-eligible without it. EXPORT: per-seller CSV of their own book, admin CSV across the tenant, plus the CCPA per-contact data export. No proprietary formats, no export paywall.

## Config resolution layer (product defaults -> tenant -> seller) powering vertical-agnostic behavior
**Verdict:** ADOPT - v1. This is what makes 'vertical-agnostic core' true rather than aspirational, and it is what lets us ship all-time leaderboard now without foreclosing monthly resets.  ·  **Complexity:** medium

**Why it matters here:** Two Phase 0 requirements collide: the pipeline is a COMMON CONFIGURABLE TEMPLATE that each seller can adjust for themselves, and the core must stay vertical-agnostic so a second vertical can be added without a rewrite. Meanwhile the cold-after-7-days rule and the loss-reason list are explicitly configurable. Without one resolution primitive this becomes settings scattered across six tables.

**Behavior spec:** One typed settings resolver: effective(key, tenant, user) = user override ?? tenant value ?? product default, with the UI always showing which level a value came from and a one-click 'reset to team default'. Governs: pipeline definition (stages, order, colors, is_closed_won / is_closed_lost flags, required-fields-to-enter gating), cold threshold (default 7 days), loss reason list (the six base reasons, editable), business hours, notification preferences, leaderboard period (all-time in v1 - the field exists so a monthly reset is a config change, not a redesign). Multiple typed pipelines are the same config object instantiated twice (FE and IUL today, a second vertical later), and an opportunity points at a pipeline_id - so pipelines are a view/config over one deal model, per pattern 8. Hard limit to avoid blank-canvas bloat: configuration edits existing typed structures; it does NOT let a user invent arbitrary objects or build a condition-builder.

## i18n readiness without shipping a second language
**Verdict:** ADOPT - v1 for the infrastructure only. Explicitly REJECT shipping a Spanish translation in v1; the point is that adding it later is a catalog file, not a refactor.  ·  **Complexity:** simple

**Why it matters here:** UI is en-US now, Spanish later was stated up front - and a meaningful share of US life-insurance telesales runs in Spanish, so this is a real near-term ask, not hypothetical. Retrofitting i18n into a vibecoded app with hardcoded strings is a full-app rewrite; doing it from day one is nearly free.

**Behavior spec:** All user-facing strings live in one en-US catalog behind a t() call from the first commit - no literals in components. Keys are semantic (leaderboard.podium.rank_label), not English-text-as-key, so translation doesn't break on copy edits. Pluralization and interpolation use ICU message format from the start ('{count, plural, one {# lead} other {# leads}}'). Currency, dates and numbers go through locale-aware formatters, never manual concatenation - and Earnings always renders as USD with a single shared money formatter so the leaderboard, kanban card, and dashboards can never disagree on format. Layout tolerates ~30% string expansion (no fixed-width buttons, no text baked into images). Content that is DATA stays untranslated: stage names, loss reasons, and carrier names are tenant config, not strings. No Spanish bundle, no language switcher, no RTL work in v1.

## Accessibility to WCAG 2.1 AA, enforced on a defined critical path
**Verdict:** ADOPT - v1 scoped to the critical path. Reject a full-app AA audit as v1 scope; the critical-path subset captures the compliance and quality value at a fraction of the cost.  ·  **Complexity:** medium

**Why it matters here:** This is a workplace tool for ~50 US employees, which puts it squarely in ADA/Section-508-adjacent territory for any agency selling to larger partners - and 'is it accessible?' is a procurement question that can stall a deal. Beyond compliance, the same work (keyboard operability, focus management, contrast) is exactly what makes the palette and shortcuts feel good.

**Behavior spec:** AA enforced on the critical path: login, kanban board, lead detail + timeline, call/SMS actions, My Day, leaderboard, and all forms. Concretely: full keyboard operability including a keyboard alternative to kanban drag-and-drop (focus card, press 1-9 or use a Move to stage menu - drag must never be the only way to advance a deal); visible focus rings everywhere; 4.5:1 text contrast including on the podium's gold/silver/bronze treatments and on the dark kiosk theme; stage and status NEVER communicated by color alone (the cold badge carries a label and icon, not just a red dot); form errors programmatically associated with their fields; live regions announcing realtime arrivals politely ('New lead - Ellen Rhodes') without hijacking focus mid-typing; prefers-reduced-motion honored by the Closed-Won celebration so confetti degrades to a static banner. Automated axe checks in CI on those routes plus one manual keyboard/screen-reader pass per release. Kiosk/TV view is exempt from keyboard requirements (it is non-interactive) but not from contrast.

## Dark mode
**Verdict:** ADOPT LATER for app-wide dark mode - it does not earn v1 scope against speed-to-lead work. ADOPT NOW for the theming token layer and the dark kiosk view, which does earn its place.  ·  **Complexity:** simple

**Why it matters here:** Honest assessment: for a daytime inside-sales tool, dark mode is a preference, not a problem-solver - and our house rule says a feature that can't name its concrete problem gets cut. BUT one variant does solve a real problem: the kiosk/TV leaderboard runs all day on a wall-mounted screen in a sales floor, where a white background is glare and the podium needs to read from 20 feet.

**Behavior spec:** v1 ships a token-based theming layer (semantic color tokens, no hardcoded hex) and exactly ONE dark surface: the full-screen kiosk/TV leaderboard, which is dark by default with high-contrast rank typography, large podium avatars, and an animated Closed-Won celebration overlay designed for across-the-room legibility. The rest of the app is light-only in v1. Because colors are tokenized and contrast pairs are already defined for the dark kiosk, a full app-wide dark theme later is a second token set plus a preference toggle (system / light / dark) - a bounded job, not a redesign.

## Graceful degradation on poor mobile connections (resilient write queue, not offline-first)
**Verdict:** ADOPT - v1, at exactly this scope. The idempotency keys and the four queued write types are the whole feature.  ·  **Complexity:** medium

**Why it matters here:** A seller logging a call disposition from a parking lot on one bar must not lose the note - losing field notes is precisely the CRM data rot we are trying to kill. But full offline is a different animal (see the next row); what is actually needed is that flaky beats broken.

**Behavior spec:** Narrow, well-defined resilience: (1) every mutating request carries a client-generated idempotency key so a retry after a timeout can never double-log a call or double-send an SMS; (2) writes that fail on network go into a local queue with automatic retry and a visible 'Saved locally - will sync' chip on the affected item, applied to the high-value writes only: notes, call dispositions, appointment outcome, stage change; (3) a global connection banner with manual retry; (4) reads of the last-viewed lead detail and My Day are served from cache on reconnect failure, clearly stamped 'Last updated 12 min ago'; (5) actions that require the network to mean anything - place a call, send SMS, enroll in sequence - are disabled offline with a plain reason rather than queued, because queueing an outbound comm creates TCPA timing risk. Sync conflicts resolve last-write-wins per field with the event log preserving both, since single-owner silos make true conflicts rare.

## Full offline-first PWA with local database and background sync
**Verdict:** REJECT for MVP. High complexity, marginal value for a phone-based inside-sales team, and it competes for scope with speed-to-lead and the leaderboard - the two things that actually sell this product.  ·  **Complexity:** high

**Why it matters here:** Tempting for a 'mobile' product, but it does not match this user. These are US inside-sales agents on a dialer working leads that decay in minutes - if they are offline they cannot call, and if they cannot call the CRM has nothing useful to do. The cost is a local replica, sync engine, conflict resolution, and migration story for a scenario with near-zero business value.

**Behavior spec:** Not built. The resilient write queue above covers the realistic failure mode. Revisit only if a future vertical involves genuine field work (in-home final expense appointments in rural coverage gaps is the plausible trigger) - at which point the event-sourced backbone already provides the replay semantics a sync engine would need.

## Observability and error telemetry inside the <$100/month envelope
**Verdict:** ADOPT - v1, in the lightweight form described. The Integration Health panel doubles as a demo asset: it visibly proves the Aloware integration is alive.  ·  **Complexity:** medium

**Why it matters here:** This system's most valuable behavior is invisible plumbing - Aloware webhooks writing to timelines. When it breaks, nobody files a ticket; sellers just quietly stop trusting the timeline, and the CRM rots. We need to find out before the client does, without blowing the infra budget.

**Behavior spec:** Structured JSON logs with tenant_id, user_id, event_type and a request/correlation id threaded from webhook receipt through projection update. Client and server error capture via a free-tier error tracker with release tagging and PII scrubbing (phone numbers, emails, transcripts and recording URLs are redacted before they leave the app - non-negotiable given CCPA). An admin-only Integration Health panel in-product showing: last Aloware webhook received per type with age, dead-letter queue depth with a retry action, ping-post intake rate over 24h, realtime connection count, and the five performance budgets with current p95. One alert rule that matters: no call webhooks received in 60 minutes during business hours. Sampled tracing only; no APM vendor. Cost ceiling ~$0-25/mo on free/hobby tiers at 50 users.

## Deep-linkable URL state and clean handoff to the Aloware Talk Chrome extension
**Verdict:** ADOPT - v1. Nearly free if decided now; a tedious sweep across every component if discovered during Aloware integration testing.  ·  **Complexity:** simple

**Why it matters here:** We are NOT an Aloware native partner - there is no embeddable softphone. Our click-to-call story is (a) the Two-Legged Call API and (b) the Aloware Talk Chrome extension detecting numbers on the page. That extension only works if our pages render phone numbers as real, well-formed, detectable text. This is a concrete constraint that has to be honored at the component level, everywhere.

**Behavior spec:** Every meaningful view is addressable and shareable within silo rules: /leads/{id}, /pipeline?stage=quoted&cold=true, /leaderboard?view=kiosk, /my-day?date=2026-08-03. Filters, sort and open panels live in the URL so a supervisor can send an admin a link, and so browser back behaves. Phone numbers render as tel:-linked, properly formatted US text nodes (never split across spans, never image/icon-only, never obfuscated) so Aloware Talk can detect and overlay its call button on any of our pages; the same number carries a data attribute with our contact id so the returning webhook can be matched to the right lead. Our own Call now button uses the Two-Legged Call API path and is always present, so the extension is an accelerator rather than a dependency.

## Purposeful empty states and inline coaching (zero-state as a feature)
**Verdict:** ADOPT - v1. Trivial cost, and it is disproportionately visible in demos and in week-one adoption.  ·  **Complexity:** simple

**Why it matters here:** A 50-seller rollout means 50 people seeing an empty board on day one, and the demo tenant is only empty where it matters. Empty states are where a CRM either teaches its own model or looks unfinished - and they cost almost nothing.

**Behavior spec:** Every list, column and panel has an authored empty state with a next action, in en-US microcopy: empty board -> 'No leads yet. Import your book or add your first lead.' with both buttons; empty timeline -> 'No activity yet. Call now to start the conversation.'; empty stage column -> a one-line description of what belongs there; leaderboard with no closed deals -> 'No Earnings recorded yet this period. First one on the board sets the pace.'; merge review queue empty -> 'No duplicates found - nice.'; filtered-to-nothing -> distinguishes 'no results for these filters' (with clear-filters) from 'nothing exists yet'. Error-empty is a third, distinct state.

## In-app notification + celebration layer (with browser push deferred)
**Verdict:** ADOPT - v1 for the in-app/realtime layer including celebrations; ADOPT LATER for browser push and email digests. The celebration is a demo centerpiece and a retention mechanic, not decoration.  ·  **Complexity:** medium

**Why it matters here:** Two things must interrupt a seller: a fresh purchased lead (minutes of value) and a missed call from a lead in play. One thing must interrupt everyone: someone just closed. Event-driven celebration on Closed-Won is a committed pattern and is the emotional core of the leaderboard being public.

**Behavior spec:** A single notification service consuming the event backbone, with three tiers. (1) URGENT, private, interrupting: new inbound lead assigned to me, missed call from an existing lead, appointment starting in 15 minutes - a persistent toast with a one-tap Call now. (2) AMBIENT, private: SMS reply received, call transcript/AloAi summary ready, lead went cold, sequence auto-paused because the lead replied. (3) SOCIAL, tenant-public: Closed-Won fires a celebration - confetti + the seller's name + the amount on the closer's screen, a lighter banner for everyone else, and a full-motion takeover on the kiosk/TV - plus a rank-change nudge to anyone who moved on the leaderboard ('Danielle passed you - you're #4'). All notifications respect the silo rules: the social tier carries name + amount + rank only, never lead identity. Per-user mute controls per tier. Browser/native push and email digests are NOT in v1 - in-app + realtime only.

## Saved views, advanced filters and bulk actions
**Verdict:** ADOPT LATER (v1.1). Ship simple stage/cold/source filters on the board in v1; defer saved views and bulk operations until real books are large enough to need them.  ·  **Complexity:** medium

**Why it matters here:** Genuinely useful once a seller has 500+ leads ('all cold FE leads in TX I haven't touched in 14 days, enroll them in the reactivation sequence'), but in month one a seller has 40 leads and the board plus Cmd+K covers them. Recycling cold/lost leads is explicitly a MANUAL action in the MVP, which removes the strongest argument for bulk tooling in v1.

**Behavior spec:** When built: a filter bar over the same query primitives the board and My Day already use (stage, source, cold status, consent status, premium range, last-touch window, state/timezone), saveable per user as named views pinned to the sidebar; multi-select on board and list with bulk stage change, bulk sequence enroll (consent-guarded per record, with a per-record skip report), bulk tag, bulk export. Bulk over ~10 records requires explicit confirm and is not undoable via the toast - it produces a reversible batch job entry instead.

## User-facing custom object / custom field builder and a generic automation condition builder
**Verdict:** REJECT for MVP, and say so out loud in the spec. Adopting it would import the precise bloat we positioned against, and it would push configuration complexity onto a 50-person agency with no admin team.  ·  **Complexity:** high

**Why it matters here:** This is the exact trap on our anti-pattern list: blank-canvas data models and 'simple to use, brutal to administer'. GoHighLevel's power is also why agencies drown in it. Our differentiator is that an FE agent opens the app and it already understands FE - not that they can model insurance themselves.

**Behavior spec:** Not built. Vertical flexibility is delivered instead by the config resolution layer (typed pipelines, configurable stages with closed-won/closed-lost flags and required-field gating, editable loss reasons, configurable cold threshold) and by a fixed set of typed fields per vertical shipped as a template. Automation is a short plain-English trigger vocabulary bound directly to stages and events, delivered as ready-made TEMPLATES (new lead -> immediate SMS + call task; appointment no-showed -> follow-up sequence; lead went cold -> reactivation task) rather than an empty rule canvas. A limited escape hatch - a handful of admin-defined extra fields on Contact and Opportunity - can be added later if a second vertical demands it, without opening the full builder.

## Notes
Scope note: 27 cross-cutting capabilities, ordered roughly by v1 priority. Verdict split: 19 ADOPT (v1), 4 ADOPT LATER (app-wide dark mode, saved views/bulk actions, browser push + email digests, fuzzy dedupe scoring), 2 explicit REJECT (full offline-first PWA, user-facing custom-object/condition builder), plus 2 hybrid calls stated as such (dark mode - reject app-wide, adopt the token layer + dark kiosk; i18n - adopt infrastructure, reject a Spanish bundle in v1).

Three capabilities are argued as architecture rather than features and should be treated as gating decisions for Phase 3/5, since retrofitting any of them is a rewrite: (1) silo enforcement as a row-level data-layer primitive with exactly one whitelisted public projection (the leaderboard), (2) the append-only event backbone that feeds timeline + automation + Earnings + leaderboard from one stream (this is also the mechanism that makes the future monthly leaderboard reset a filter rather than a redesign, per OQ-3), (3) timezone/IANA modeling, which silently determines whether the 7-day cold rule, appointment reminders, My Day and the TCPA calling window are correct.

Two deliberate tensions were resolved rather than papered over: (a) 'no confirm dialogs' is adopted for reversible work but explicitly overridden for anything that leaves the building (SMS, email, call, sequence enroll, bulk >10, import commit, CCPA delete) - the Closed-Won drag is gated by the required annual-premium field plus undo, never by a confirm; (b) 'mobile-first' is specified as an omission list (no pipeline config, no automation editing, no CSV import, no user management, no kiosk on mobile) because declaring what mobile does NOT do is what prevents the afterthought failure mode.

Highest sellability leverage in this list, in order: the seeded US life-insurance demo tenant (FE premiums $540-$1,450/yr vs IUL $2,400-$12,000/yr, ping-post/direct-mail/FB-form sources, pre-threaded call timelines with dispositions and AloAi-style summaries), the realtime Closed-Won -> re-rank -> celebration -> kiosk chain, and Cmd+K that dials. The Integration Health panel is a secondary demo asset - it visibly proves the Aloware webhook pipeline is alive, which is the claim buyers will be most skeptical of given we are not a native partner.

Unaddressed dependency for Phase 3: the undo window on Closed-Won interacts with the leaderboard projection and the celebration broadcast (an undone close must un-rank and the celebration must be retracted). This needs an explicit design decision - either hold the projection write for the 5s undo window, or emit a compensating event - and it should not be left to implementation time.
